Data integrity: making the backend last for years

Convex has no foreign keys. This is what "proper relations" means here: every reference typed and indexed, every delete deciding on purpose what happens to the children, nothing growing without a plan, and a way to notice drift before a household does.

Written 2026-11-19Branch: dev @ 04a0aee + uncommitted moderation / Plus capDeployment: self-hosted, Oracle Ampere ARM, SQLite

Where it stands

The data model is in better shape than most. Every relation is a typed v.id(...), every child table that is deleted with its parent has an index to find it by, home deletion drains in bounded self-scheduling batches, account deletion is a bounded step machine, and links that must survive (money, shopping) are detached rather than deleted on purpose, with the reason written beside the code.

What is missing is the layer around it: no off-box backup, no tests, no integrity check, files that are never deleted when their row goes, auth tokens that are never cleaned, and a handful of reads that grow with a household's age and will hit Convex's limits in a busy house after a few years. None of it needs an app release; all of it can ship backend-only and stay safe for every old build.

3high@convex-dev/auth 0.0.87, refreshTokens.js, sessions.jsEvery token refresh (hourly access token) inserts a new authRefreshTokens row; the library deletes them only when the whole session is deleted (sign-out, account delete). Schema hygiene

  • Schema validation is on (the default; no schemaValidation: false). Good: a push that does not fit the data fails instead of drifting.
  • Optional vs required is deliberate and documented at the top of schema.ts. Every home_id on household tables is required now, which makes the CLAUDE.md note about "every home_id is optional" out of date: the advice to use requireDocHome still holds.
  • Union literals are used for every fixed set except home_activity.category (a free string on purpose, explained) and reports.snapshot.message_type.
  • Written, never read: pbId everywhere; created / updated duplicate _creationTime on most tables (harmless, and clients read some).
  • Dead code: cascadeDeleteConversation has no caller.
  • Index count: highest are companion_growth (5), reports (5), home_activity (4), tasks (3 with by_pbId). Reasonable.
  • returns validators exist in companion, moderation, pro, jar, demo; missing in most of the older modules. Add them only with a test that exercises the real output, because a wrong one breaks the screen for every build.

What to borrow from MonkeyHub

MonkeyHub (also Convex, self-hosted) ran a seven-phase integrity programme in October 2026. Its scale is chat-app scale; NestZone is a household app with an order of magnitude less data per user. Take the mechanisms, not the machinery.

MonkeyHub pieceTake it?Why
schemaRefs.ts + referenceRules.ts + its test (every v.id path gets cascade / setNull / history / softRef / file, and a cascade needs an index)Yes, as isSmall, pure, and it is what turns "proper relations" into something enforced. NestZone has ~110 reference paths.
integrity.ts: weekly paged scan with counters, resumed if stalledYes, simplifiedAt NestZone's size one action paging each table is enough; keep the "expected dangling vs violation" split.
sweep.ts (continueSweep, chain cap)YesThe self-scheduling pattern NestZone already uses, made reusable, with a cap so a sweep can never loop forever.
retention.ts and its testsYes, the patternFor poll rounds, auth tokens, reports.
vitest + convex-test, edge-runtime environmentYes, as isDrop-in config.
Deletion engine with tombstones, per-row sub-transactions, 5-minute re-driveNoNestZone's home purge and account steps already do the important part (access removed at once, rows drained in batches). Add the integrity scan as the watchdog instead.
fileRefs ledger with reference counts, epochs, enforce flagsNoBuilt for files shared across rooms, forwards and stickers. NestZone has two upload paths and one hold table; a reaper that checks known fields is enough. Keep its safety idea: the reaper only logs until an env flag says otherwise.
Presence and profile tablesNoDifferent problem.

Phased plan

Every phase is backend-only and safe for every app version in use: new tables, fields and indexes are added; nothing an old build sends or reads is narrowed; data changes run as self-scheduling batches (or @convex-dev/migrations), are idempotent, and are dry-run first. Anything that would narrow an argument waits for inbox:versionCensus and gets a row in DEPRECATIONS.md.
